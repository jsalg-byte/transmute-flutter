# Transmute Flutter parity matrix

This is the delivery map for expanding the focused Flutter demo toward the
existing Transmute product. A slice is not considered complete merely because
the Expo product has an endpoint: Flutter needs a deliberate domain contract,
mock behavior, production adapter, loading/empty/error states, and responsive
UI.

## Verified contract boundaries

- The existing Expo API is **not** compatible with the original Flutter demo
  contract. Expo uses `/v1/*`, returns an aggregate `GET /v1/record`, and uses
  plan-day IDs to start sessions. The earlier Flutter API repository expects
  unrelated `/workout-plans` and `/workout-sessions` payloads. Production mode
  must therefore use an explicit Expo adapter; it must not silently point the
  old client at the existing API.
- Plan prescriptions are per plan-day exercise and contain target sets, reps,
  and optional target weight. The audited product does not persist a plan rest
  duration. Flutter's rest timer is deliberate local session/device state.
- Muscle readiness is derived only from completed, non-warm-up sets in the
  last 48 hours. Do not infer recovery from a scheduled plan or an active
  session.
- The record endpoint contains the current product surfaces listed above, but
  goals, reviews, training blocks, recovery check-ins, and adherence have
  separate endpoints. Their presence in the Fastify API does not establish a
  Flutter UI requirement or UX contract by itself.
